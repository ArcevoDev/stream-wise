P0-1. Versioned domain catalogs + weight sets (CLAUDE.md "What NOT to build" fix)
--------------------------------------------------------------------------------
The spec's central rule — "no hardcoded 3-stream enum or hardcoded JAMB
subject lists in code; these are versioned catalog tables" — is currently
violated end-to-end.

  a) SubjectCatalog table (academicSession FK, e.g. "2025/2026"): subject
     code, name, streamCategory, isCore, isTradeSubject, isActive.
     Replace hardcoded Subject enum usage in SubjectScore/JambCourseSubject
     (keep the enum as a stable reference OR migrate to String + FK —
     DECISION REQUIRED; see Known Decisions below). - whichever is best and most scalable
  b) Stream catalog: labels, descriptors, career lists per stream, versioned
     by academicSession. Kills the hardcoded stream literals in saw.ts and
     confidence.ts and the manual streamEnumMap in recommend.controller.ts.
  c) AhpWeightSet table: pairwise matrix (Json), derived weights (Json),
     cr, lambda, version, createdAt, immutable once referenced. Seed one
     row from the current PAIRWISE_MATRIX (ω ≈ [0.540, 0.297, 0.163], CR
     ≈ 0.007). Engine consumes weights from here, never from module-load
     constants (delete AHP_WEIGHTS / W_ACADEMIC / W_RIASEC / W_PERSONALITY
     module-level constants).
  d) JambRequirement versioning: add admissionCycle to JambCourse (or a
     versioned JambRequirement table). Current JambCourse + JambCourseSubject
     join is relational but global — one cycle only.
  e) RIASEC→stream affinity mapping and personality→stream mapping become
     versioned config rows (part of the weight set or catalog), not literals
     in riasec.ts / saw.ts.

P0-2. Engine seam re-wiring (spec-shaped, data-driven, testable)
--------------------------------------------------------------------------------
Match the CLAUDE.md engine contract. Purity is already intact; the seams are
wrong.

  a) computeAhpWeights(pairwiseMatrix): takes the matrix as a parameter,
     THROWS when CR > 0.10 (Saaty rejection, §2.3.6) instead of returning an
     ignored `consistent` flag.
  b) scoreStreams(studentProfile, weights, subjectCatalog) or equivalent:
     computeSAW must accept weights + stream→criterion mappings as arguments.
     No imports of engine-internal weight constants.
  c) validateJambPrerequisites(recommendedStream, careerGoal,
     jambRequirements): extract from jamb.controller.ts into a PURE engine
     module (it currently does inline set-difference inside a Prisma route
     handler).
  d) explainRecommendation(rankedStreams, weights): per-criterion
     contribution breakdown per stream (Academic / RIASEC / Personality),
     feeding guidanceInsight. Currently generateGuidanceInsight is narrative
     prose without a contribution breakdown.
  e) Single source of truth for stream identity: engine "Science" strings,
     DB AcademicStream enum, and streamEnumMap collapse into one typed
     mapping derived from the stream catalog (P0-1b).

P0-3. Methodology integrity pinning (invisible gaps — research-validity issues)
--------------------------------------------------------------------------------
These are silent divergences between the code and the documented thesis
methodology. An examiner re-running the math would find them.

  a) Academic-by-stream scoring: recommend.controller.ts gives all three
     streams the SAME core-weighted baseline (jss3*0.4 + SS1 English+Maths
     avg*0.6) and upgrades only the student's reported currentStream to
     weightedAcademicScore. If no stream is reported, the academic criterion
     is identical across streams and cannot differentiate. Pin ONE
     documented rule (per-stream academic score = jss3*0.4 + that stream's
     SS1 subjects*0.6, per §3.5.3) and implement it uniformly.
  b) DEFAULT_PERSONALITY injection: a student who skips BFI gets neutral
     60/60/60/60 data fed into SAW at FULL weight (0.163) — silent bias.
     Fix: either require BFI before recommendation, or renormalize the
     weight vector over the criteria actually present. Never inject fake
     data at full weight.
  c) Confidence CL rescaling [50,100]: formula exists (rawCL 1/3 → 0.5).
     Document "why 50 min" in the engine + UI (already flagged in
     output.txt; make it a documented constant, not magic math).
  d) Personality→stream mapping contradiction: saw.ts Science = (O+C)/2 but
     schema comment says Science→O only. Resolve and record the canonical
     mapping (→ versioned config in P0-1e).
  e) neuroticismScore is stored but never consumed by SAW. Decide: include
     it in the methodology (5-factor) or document its exclusion. - include in methodology - if that's best
  f) Subject enum contains legacy artifacts (CIVIC_EDUCATION "superseded")
     — resolves naturally when SubjectCatalog becomes the source of truth
     (P0-1a).

P0-4. Consent + career-goal data model (ethics + validator input)
--------------------------------------------------------------------------------
  a) Consent recording: Student (or ConsentRecord table) gains
     consentVersion, consentedAt, and per-point consent booleans (the
     landing page spec lists 4 points). Assessment flow gates on consent.
     No consent artifact exists today — the ethics card is a marketing page.
  b) careerAspiration: schema field exists but NOTHING collects it in the
     client flow, and the JAMB validator ignores it (student browses a
     catalog and picks a course). Capture it (register or profile step),
     store it, and drive validateJambPrerequisites(careerGoal, ...) from it
     per the spec (P0-2c).

P0-5. Audit version linkage + re-scoring path
--------------------------------------------------------------------------------
  a) RecommendationLog gains ahpWeightSetId (FK → P0-1c) and
     jambRequirementVersion / admissionCycle reference. Today it snapshots
     weights as JSON but cannot be correlated to the exact weight set or
     JAMB cycle that produced it.
  b) instrumentVersion on RiasecResponse + BfiResponse (spec-required) so a
     future item-set change cannot corrupt historical responses. Question
     sets (RIASEC_QUESTIONS / BFI_QUESTIONS in engine code) need a version
     that gets stamped into responses and profiles.
  c) Re-scoring path: RiasecResponse / BfiResponse rows are write-only today
     — never re-read. The 100-profile validation study (§3.8) needs a
     version-aware re-scoring entry point (compute profiles from raw rows
     via the existing computeRIASEC / computeBFI).
