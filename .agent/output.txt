WHAT THE SYSTEM IS
--------------------------------------------------------------------------------
A Weighted Decision Support System (DSS) that recommends an academic stream
(Science / Humanities / Business) to Nigerian SS2 students using an
AHP-SAW multi-criteria decision engine. Inputs: JSS3/SS1 academic scores,
a 48-item RIASEC vocational interest quiz, and a 20-item BFI personality
questionnaire. Output: a ranked stream recommendation with confidence level,
plain-language guidance, AHP weight transparency, and a JAMB O'Level subject
combination validator against a seeded university-course catalog.

STACK
  Frontend: React 18 + Vite 5 + TailwindCSS + React Router 6 + Recharts + Axios
  Backend:  Express 4 + TypeScript (ESM) + Zod validation
  Database: PostgreSQL + Prisma 7 (adapter-pg, generated TS client)
  Engine:   Pure TS modules (AHP, SAW, RIASEC, BFI, confidence) — no DB/HTTP deps
  Auth:     JWT (7d expiry, bcrypt-12 password hashing), role field on Student
  Deploy:   Vercel (static client) + server behind reverse proxy (Railway/Cloudflare)

WHAT'S ALREADY STRONG (keep — these are thesis strengths)
--------------------------------------------------------------------------------
1. Clean engine separation — AHP/SAW/RIASEC/BFI are pure, testable ESM modules
   with zero DB or Express coupling. This is exactly what an examiner wants to
   see and it makes unit testing trivial (currently missing, see Gaps).
2. Auditable recommendation logs — RecommendationLog snapshots inputs, weights,
   and algorithm version as JSON. This closes the "explainability gap" and is a
   genuine differentiator for a final-year project.
3. Fully normalized subject scores (SubjectScore rows + unique constraint) —
   adding a subject is an INSERT, not a migration.
4. Raw psychometric responses persisted separately (RiasecResponse/BfiResponse)
   — supports re-scoring and the 100-profile validation study from the thesis.
5. Zod validators derive enums directly from Prisma's generated enums — enum
   drift is structurally impossible.
6. Security posture is reasonable: helmet, CORS allowlist, rate limiting,
   JWT with bcrypt, 100kb body limits, audit-log table.
7. In-flight improvement (uncommitted): stream-specific academic affinity.
   The old SAW fed the same weightedAcademicScore into all three streams;
   the new code derives per-stream academic scores (core-subject weighted
   baseline + the student's reported currentStream). This makes the academic
   criterion actually stream-aware. Finish and commit this.

MAIN GAP — NO ADMIN/COUNSELOR/ANALYTICS SIDE (the big missing piece)
--------------------------------------------------------------------------------
The schema already models Counselor, School, Admin, AuditLog and all the
data needed for oversight. NONE of it is exposed:

  • No admin/counselor routes or controllers (all /api routes are student-only)
  • No role-based access control middleware (roles exist on Student but the JWT
    only carries id/email/fullName, and authenticateToken never checks role)
  • No dashboard, analytics, or data-visualization UI
  • AuditLog is defined but never written (no code inserts audit records)
  • Counselor/student assignment exists in the schema but has no API/UI
  • lastLoginAt is tracked but unused
  • RecommendationLog history endpoint exists (GET /recommend/history) but the
    client has no page consuming it

This is the single highest-value build for the project: an Admin Dashboard +
analytics layer would give the thesis a complete stakeholder story (student →
counselor → school admin → platform admin) and a rich results/data chapter.

SMALLER IMPROVEMENTS SPOTTED (quick wins)
--------------------------------------------------------------------------------
  • auth.controller.ts Bug 2.1 workaround — schoolName is concatenated into
    careerAspiration ("[School: X] — aspiration") because Student has no
    schoolName column. Proper fix: create/link a School record from schoolName
    in register, or add a dedicated schoolName field. Currently the school
    stakeholder model is effectively unused.
  • register endpoint sets role implicitly (always STUDENT) — fine, but ensure
    no client payload can set role (Zod schema doesn't accept it — good).
  • getMe returns schoolId/counselorId but nothing consumes them.
  • Results.tsx hardcodes STREAM_SUBJECTS per stream for JAMB validation while
    the server has the real SubjectScore rows — the client should send the
    student's actual subject scores instead of a static list, so validation
    reflects reality (currently a student could "pass" with subjects they never
    took). This is a correctness issue worth fixing alongside the dashboard.
  • JAMB validator ignores trade subjects and DIGITAL_TECHNOLOGIES /
    CITIZENSHIP_AND_HERITAGE (new NERDC core) — worth a review pass.
  • Scores form only collects SS1 scores + JSS3 overall average; SubjectScore
    model supports JSS3 per-subject rows. Using them would make the academic
    criterion genuinely normalized.
  • api/errors.ts — no 429 (rate-limit) handling; user sees generic message.
  • Confidence CL formula rescales to [50,100]; document the mapping in the
    UI (it already shows the number, but the "why 50 min" is non-obvious).
  • No .env.example for the client (VITE_API_BASE_URL) — add one.
  • README is thin for a final-year project — add architecture diagram (ASCII),
    API reference table, test instructions, and a "validation study" section.

ARCHITECTURE NOTES / RISKS
--------------------------------------------------------------------------------
  • A single Student table carries role (STUDENT default) — COUNSELOR and ADMIN
    would also need login. Either reuse Student with a role check, or introduce
    the separate Counselor login path already implied by the schema. Simplest
    for the project: extend auth to accept role from the Student table and seed
    an admin account. Keep the design decision explicit in the thesis.
  • Prisma 7 generated client is committed under server/prisma/generated — make
    sure "prisma generate" is part of deploy (vercel.json already does it).
  • server/scripts/fix-prisma-imports.js post-build step — confirm it survives
    a clean build; CI would catch it.
  • The `server` workspace package is imported by the client (server/enums) —
    this couples the client build to the server workspace; fine for a monorepo
    but note it in the thesis build pipeline.
